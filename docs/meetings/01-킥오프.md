## 3. 쟁점별 논의와 결정

### 쟁점 1. 무엇부터 하는가

- PM: 시나리오 골든 테스트를 0순위로 두고, 통과 전에는 다른 스프린트 착수에 반대한다.
- 테크리드: 병렬 개발 전에 계약 동결(WP0)을 순차로 끝내야 한다. 그렇지 않으면 useTrip.ts, types.ts, constants.ts, App.tsx에서 모든 패키지가 충돌한다.
- 디자이너: 화면보다 먼저 ui.tsx를 토큰과 공통 컴포넌트로 다시 짜야 한다.
- QA: core 경계 규칙과 테스트 하네스가 먼저다.

**결정.** 네 요구를 '기반 작업(F)' 하나로 묶어 병렬 개발 전에 순차로 끝낸다. 기반 작업은 계약 동결, 브랜드 변경, 토큰·공통 컴포넌트·아이콘·폰트, 테스트 하네스, core 경계·디자인 규칙 테스트, 시나리오 데이터, 골든 테스트 골격을 포함한다. 골든 테스트는 기반 작업에서 todo로 만들어 두고, WP3(추출 골든)와 WP4(계획 골든)가 통과시킨다. 통합 게이트에서 todo를 풀고 전부 통과해야 병합한다.

**기각.** "골든 테스트 통과 전 다른 작업 착수 금지"(PM)는 받지 않는다. 골든 수치는 planner를 다시 짜는 WP4의 결과물이라, 그것을 기다리면 여섯 패키지가 직렬로 선다. PM 요구의 취지인 "숫자가 틀린 채 발표하지 않는다"는 통합 게이트에서 지킨다.

### 쟁점 2. 스프린트 구조

- PM: 1단계 보강 → 2차 → 3차 순서의 스프린트 셋.
- 테크리드: 기능 영역별 병렬 패키지 여섯.

**결정.** 기능 영역별 6개 패키지를 병렬로 돌린다. 각 패키지 안에서 MVP → 2차 → 3차 순서로 일한다.

**기각.** 단계별 스프린트는 받지 않는다. 같은 파일(planner, 지도, 스토어)을 단계마다 다시 열어 소유권이 겹친다. PM이 걱정한 시나리오 연속성은 패키지 안 우선순위와 통합 게이트로 지킨다.

### 쟁점 3. 상태 모델

- 테크리드: 여행방 문서 + 연산(op) 로그, 기능별 순수 리듀서, 스토어 4개(session / trips / live / ui).
- PM: 날짜별 기점, 수동 순서, lastEditedAt을 스키마 v2 하나로 묶자.
- QA: 판정 로직은 전부 순수 함수로.

**결정.** 테크리드 안을 채택한다. 모든 변경은 직렬화 가능한 op `{id, tripId, actorId, at, seq?, type, payload}`로 만들고 `applyOp(doc, op)`로만 적용한다. 리듀서 안에서는 시각과 ID를 만들지 않는다. 수동 편집(순서, 시각, 체류, 날짜, 수단)은 plan이 아니라 spot과 day 설정에 저장한다. 그래서 재계산해도 남는다. plan은 동기화하지 않고 기기마다 다시 계산한다.

동시 편집의 '나중 저장 우선'은 op를 seq 순서로 적용하되, 필드마다 마지막 적용 시각(op.at)을 기록해 더 이른 저장이 늦은 저장을 덮지 않게 한다(FR-503과 FR-703이 같은 lww 함수를 쓴다).

**기각.** seq 순서만으로 LWW를 판정하는 안(테크리드 원안)은 받지 않는다. 오프라인에서 먼저 저장한 편집이 늦게 도착했다는 이유로 최신 편집을 덮는다. 명세의 '저장' 시점과 어긋난다.

### 쟁점 4. 그룹 동기화

- 테크리드: SyncTransport 뒤에 기본 LoopbackTransport(서버 없음), 선택형 HttpPollingTransport + 의존성 없는 node 서버.
- PM: 시연은 단일 기기로 충분한가?

**결정.** LoopbackTransport를 기본으로 한다. 시연·테스트·웹 export가 이것만으로 끝난다. 루프백에는 '네트워크 끊기' 토글과 순서 뒤섞기·중복 주입을 넣어 FR-304 재전송 큐와 순서 보정을 한 기기에서 보여준다. HttpPollingTransport와 `server/sync-server.mjs`(node:http만 사용)는 WP2의 마지막 순위로 만든다. EXPO_PUBLIC_SYNC_URL이 있을 때만 켜진다. 서버는 node --test 안에서 포트 0으로 띄웠다가 닫는 방식으로만 검증한다. WebSocket은 쓰지 않는다.

### 쟁점 5. 외부 의존 중립 인터페이스

- 네 명 모두 같은 방향이다. 키가 없으면 결정적 모의 구현, 키가 있으면 실제 구현.

**결정.** 인터페이스는 `src/core/ports.ts` 한 곳에 모은다: Clock, IdGen, Rng, Hasher, PlaceProvider, RouteProvider, ExtractionProvider, RecommendProvider, DiaryWriter, AuthProvider, SyncTransport, LocationProvider, PhotoProvider. 구현 선택은 `src/services/registry.ts` 한 곳에서 한다. core 함수는 전부 제공자를 인자로 받는다.

AI 실제 구현은 키를 번들에 넣지 않는다. `EXPO_PUBLIC_AI_PROXY_URL`로 프록시를 부르는 어댑터만 둔다(테크리드 지적 반영). 지도·경로 실제 구현은 기존 구글 어댑터를 유지한다. 국내 SDK(카카오·네이버) 선정과 경로 API 예산은 명세 미결정 항목이라 이번에 정하지 않는다.

### 쟁점 6. 저장 키와 마이그레이션

- PM·테크리드: persist 키를 바꾸되 구 키 데이터를 옮기자.
- 디자이너·QA: 옮길지 초기화할지 정하자.

**결정.** 새 키 `young-trip/*`(버전 2)로 바꾸고 구 키 `yeojeong-proto-v1`은 첫 실행 때 지운다. 데이터는 옮기지 않는다. 온보딩에 "이전 프로토타입 데이터는 옮기지 않았습니다"를 한 번 띄운다.

**기각.** 이관은 받지 않는다. 실사용자가 없다. 구 기기 토큰은 추측 가능해 보안 요구를 어기므로 옮기면 안 된다. 단일 기점과 plan 내장 모델을 op 로그로 바꾸는 비용에 비해 얻는 것이 없다. 리허설은 '시연 리셋'으로 처음 상태를 만든다.

### 쟁점 7. 시나리오 골든 수치는 얼마나 정확해야 하는가

- PM·QA: 14 → 11/3, 제외 사유, 10/18 타임라인을 정확히 재현해야 한다.
- 테크리드: 정확 일치로 갈지 근사로 갈지 정하자. 수치를 맞추려고 데이터를 조정하는 것은 기록해야 한다.

**결정.** 다음은 정확히 일치해야 한다.

### 쟁점 9. 자동 선별(FR-403)을 어떻게 해석하는가

- QA: 지금의 우선순위 탐욕 배치는 "우선순위가 낮은 짧은 스팟이 들어가고 높은 긴 스팟이 빠지는" 결과를 낸다. 허용할지, 엄격한 우선순위 컷으로 갈지 정하자.

**결정.** '교환 불변식'을 기준으로 한다. 제외 스팟 E마다, E보다 우선순위가 낮은 비고정 확정 스팟 K 하나를 빼고 E를 넣어 수용량 안에 들어가는 교환이 있으면 안 된다. 탐욕 배치 뒤에 이 교환을 찾아 고치는 보정 단계를 둔다. 우선순위는 고정·날짜 지정 → 제안자 수 많은 순 → 등록 이른 순이다. 속성 테스트로 검증한다.

**기각.** 현행 탐욕 배치 그대로는 받지 않는다. 명세의 제외 순서를 어기는 결과가 나오고, 명세가 경고한 "내가 말한 데가 없어졌다"가 된다. 엄격한 컷(앞 순위가 빠지면 뒤 순위도 모두 뺀다)도 받지 않는다. 들어갈 수 있는 스팟까지 빼게 되어 "수용량을 넘는 만큼만 뺀다"는 명세와 어긋난다.

사유 코드는 다음과 같다. 'dayFull'은 가장 싸게 들어갈 수 있던 날짜를 기준으로 쓴다. 사유는 `M/D` 뒤에 시간대를 붙이고 '이/가 꽉 차서'로 끝난다. 시간대(오전 12시 전 / 오후 18시 전 / 저녁)는 그날 활동시간이 둘 이상의 시간대에 걸칠 때만 붙인다. 'tooFar'는 기점 왕복이 60분 이상일 때 `왕복 N시간 M분`으로 쓴다. 나머지 코드는 'userRemoved'(사용자가 직접 뺌, 지연 조정안으로 뺌)와 'outOfPeriod'다.

### 쟁점 19. 보안 난수와 모의 인증

- 기기 토큰은 16바이트(128비트)를 base64url로 만든다.
- 초대 코드는 Crockford base32 8자(40비트)를 `XXXX-XXXX` 형식으로 만든다. 목업 예시 7K2D-9M은 6자라 30비트다. 7일 유효 링크에는 짧다고 보고 8자로 늘린다.
- 비밀번호는 salt + SHA-256(Hasher 주입)으로만 단말에 저장한다. 화면에 '프로토타입 · 단말 저장, 실제 서비스는 서버 해시' 한계를 적는다.
- 기기 토큰 원문은 화면에 보이지 않고 끝 4자리만 보여준다.
- core는 Rng와 Hasher를 주입받고, 테스트는 시드 고정 난수를 쓴다.

### 쟁점 20. FR-303 '권한 조정'은 무엇인가

- 명세 권한표에서 방장만 할 수 있는 동작은 멤버 초대, 내보내기, 삭제다. 방장 권한 위임은 미결정이다.

**결정.** '권한 조정'은 그룹원에게 초대 권한을 켜고 끄는 것(member/setCanInvite)으로 한정한다. 화면에 '프로토타입 가정'이라고 표시한다. 방장 역할을 넘기는 기능은 위임과 같은 것이라 만들지 않는다.

### 쟁점 21. 개인 모드와 그룹 모드

**결정.** 모드는 저장하지 않고 활성 멤버 수로 계산한다. 2명 이상이면 그룹이다. 개인 모드에서는 채팅과 대화 인식이 비활성이고(명세: 그룹 전용 기능은 채팅과 대화 인식뿐), 수동 등록·루트·지도는 그대로 동작한다. 방장 외 전원이 나가면 개인 모드로 돌아가고 채팅과 스팟은 유지한다. 종료일이 지나면 편집 op를 거부하고 일기·사진·지도 열람과 사진 추가·일기 편집은 허용한다.

### 쟁점 22. FR 추적표

- PM: FR마다 단계, 담당, 구현 파일, 모의 제공자, 시연 단계, 테스트 이름, 상태를 한 표에.

**결정.** 채택한다. `docs/FR-추적표.md`(프로젝트 루트 docs)를 기반 작업에서 만들고 회의마다 갱신한다. 테스트가 없는 AC는 '화면 확인' 사유를 적어야 통과로 친다(QA 제안). README의 '구현한 기능' 표는 통합 때 이 표에서 옮겨 적는다. 지금 README가 FR-301/302/303 구현을 과장한 부분도 그때 바로잡는다.

## 부록 A. 계약

패키지가 서로 기다리지 않도록 이름과 시그니처를 여기서 고정한다.

### A1. 공통 규칙

- import는 확장자 없이 쓴다. 타입만 가져올 때는 `import type`을 쓴다.
- `src/core/**`는 순수 TypeScript다. react, react-native, expo-*, zustand, @react-native-async-storage/*, `src/services/**`, `src/store/**`, `src/config.ts`를 import하지 않는다. JSX, enum, namespace, 매개변수 프로퍼티를 쓰지 않는다. `Date.now()`, `Math.random()`, 인자 없는 `new Date()`를 쓰지 않는다. 시각·난수·ID·제공자는 인자로 받는다. 경계 테스트가 검사한다.
- 화면과 feature 파일에는 16진수 색, fontWeight, fontFamily, 16 초과 라운드 숫자, 그림자 속성을 쓰지 않는다. 전부 `src/ui`를 거친다.
- 모든 스토어는 `reset()`을 가진다.
- 시각은 `appClock().now()`(ms)다. 날짜 문자열은 KST 기준 'YYYY-MM-DD', 시각은 'HH:MM'이다.

`src/core/ops/index.ts`(기반 작업)의 내용은 다음과 같다.

- `applyOp(doc: Trip | undefined, op: Op): Trip | undefined`
- `validateOp(doc, op): { ok: true } | { ok: false; reason: string }`
- `foldOps(ops: Op[]): Trip | undefined`: seq 순서로 적용하고, seq가 없는 op는 at 순서로 뒤에 붙인다.
- `isEditLocked(doc, at): boolean`: kstDate(at)가 종료일보다 뒤인지 본다.
- `LOCK_EXEMPT`: journal/*, member/leave, trip/delete
- 적용 전에 같은 op.id를 무시해 중복을 거른다.

기능 파일은 각각 `reduce(doc: Trip, op: Op): Trip`와 `validate(doc: Trip, op: Op): string | null`(null이면 허용)을 export한다. trip.ts는 `reduceCreate(op): Trip`도 둔다. `src/core/ops/lww.ts`의 `lww(prevAt: number | undefined, at: number): boolean`은 at이 prevAt 이상이면 적용한다.
