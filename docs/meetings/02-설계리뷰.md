## 3. 진행자 재확인

리뷰어 주장 가운데 로컬에서 확인할 수 있는 것은 진행자가 직접 돌려 봤다. 틀린 주장은 없었다.

| 주장 | 확인 방법 | 결과 |
| --- | --- | --- |
| react-native-maps에는 웹 구현이 없다 | node_modules/react-native-maps/package.json | main이 src/index.ts 하나이고 browser 필드가 없다. 맞다 |
| react-native-web의 Share는 navigator.share가 없으면 reject한다 | node_modules/react-native-web/dist/exports/Share/index.js 28행 | 'Share is not supported in this browser'로 reject한다. 맞다 |
| node 24는 .tsx를 불러오지 못한다 | 스크래치패드에서 .ts가 .tsx를 import하게 해서 node로 실행 | ERR_UNKNOWN_FILE_EXTENSION. 맞다 |
| @types/node는 전이 의존이고 26.x다 | node_modules/@types/node/package.json, package.json | 26.6.2이고 package.json에는 없다. 맞다 |
| 폰트 패키지를 루트에서 불러오면 전 굵기가 번들에 들어간다 | npm view로 크기 확인, npm pack --dry-run으로 파일 목록 확인 | gothic-a1 21.48MB, hahmlet 14.75MB. 400Regular, 600SemiBold, 700Bold 서브패스 폴더가 따로 있고 ttf는 각 약 2.29MB다. 서브패스 import가 가능하다 |
| 웹 digestStringAsync는 보안 출처에서만 된다 | 01 회의록 2.5절(Expo v57 문서 확인 기록) | 01에서 이미 기록한 내용과 같다 |

확인하지 못한 것이 하나 있다. 구글 경로 API가 국내 자동차·도보 경로를 주지 않는다는 점은 공개 문서 기준으로 알려진 내용이지만, 키가 없어 재현하지 못했다. 구글을 빼는 결정의 주된 근거는 명세 문구이고, 이것은 보조 근거로만 적는다.

## 5. 쟁점 논의

대부분은 이견 없이 수용했다. 이견이 있었던 것만 적는다.

### 쟁점 A. 실제 지도·경로 제공자를 무엇으로 둘 것인가 (1번, 36번)

- 명세 리뷰어: 구글을 빼고 국내 어댑터 자리만 스텁으로 둔다.
- 테크리드: 스텁만 두면 고정 규칙 "키가 있으면 실제 제공자로 바뀌는 구조"를 채우지 못한다. 키를 넣어도 아무것도 바뀌지 않기 때문이다.
- PM: 국내 SDK 선정과 경로 API 제공자는 명세 미결정이다. 하나를 구현하면 결정한 것처럼 보인다.

**결정.** 구글은 뺀다. 명세가 국내 전용, 지도 SDK 1종, 두 벌 금지를 명시했고 구글은 해외 로드맵 항목이다. 실제 어댑터는 카카오 한 종만 만든다. 장소는 카카오 로컬 키워드 검색, 경로는 카카오모빌리티 자동차 길찾기다. 도보와 대중교통은 공개 경로 API가 없어서 로컬 모델로 계산하고 estimated를 세운다. EXPO_PUBLIC_KAKAO_REST_KEY가 있을 때만 켜진다.

이것은 SDK 선정이 아니라 '프로토타입 가정'이다. 인터페이스가 중립이라 파일 하나를 바꾸면 되돌릴 수 있다. 화면(18 제공자 상태)과 추적표에 '국내 SDK 선정 미결정'을 적는다. REST 키가 번들에 들어가므로 시연 한정이라고 .env.example에 적고, 실서비스는 프록시로 옮긴다고 기록한다. AI는 01 결정대로 프록시만 쓴다. AI 키는 호출 단가가 크고 브라우저에서 직접 부를 수 없어서 기준을 달리 둔다.

카카오 문서는 WP3·WP4가 구현 전에 WebFetch로 확인한다. 실키가 없어 동작 확인은 못 하므로, fetch 주입 테스트로 요청 형식과 응답 변환만 검증하고 추적표에 적는다. 웹에서 CORS가 막히면 네이티브 한정으로 적는다.

지도 화면은 MapCanvas(react-native-svg) 한 벌이다. react-native-maps는 package.json에서 뺀다. 실제 지도 SDK 뷰는 MapCanvas props를 그대로 받는 어댑터로 나중에 붙이며, 네이티브 전용이면 .native.tsx 안에 둔다.

### 쟁점 B. 계정 탈퇴를 만들 것인가 (5번)

- 01 결정: 범위 밖. 근거는 "명세서가 범위의 유일한 기준"이었다.
- 명세 리뷰어: 비기능 데이터 보존이 탈퇴 시 처리를 요구하므로 명세에 있다.

**결정.** 01의 근거가 틀렸다. 탈퇴 동작을 2차 계정 기능으로 넣는다. 정식 계정만 탈퇴할 수 있다. 탈퇴하면 참여한 모든 방에서 본인이 올린 사진을 지우고(journal/photoRemoved), 멤버를 익명화한다(member/anonymize: 닉네임 '탈퇴한 멤버', leftReason 'deleted'). 채팅과 제안 이력은 memberId를 그대로 두어 남긴다. 두 op는 종료 잠금 예외다. 게스트는 계정이 없으므로 탈퇴 대상이 아니다.

### 쟁점 C. 작업 중 게이트를 얼마나 느슨하게 할 것인가 (17번)

- QA: 자기 파일만 보면 남의 파일을 깨뜨리는 변경을 늦게 발견한다.
- 병렬 리뷰어: 전역 게이트를 동시에 돌리면 서로 막힌다.

**결정.** 작업 중에는 자기 범위만 본다. 대신 공유 계약은 이번에 다시 동결했고 공유 파일은 통합 담당만 고친다. 따라서 패키지가 남의 파일을 깨뜨릴 경로는 공유 타입을 잘못 쓰는 경우뿐이며, 이것은 자기 파일의 tsc 오류로 드러난다. 통합 담당은 패키지가 완료를 보고할 때마다 전체 게이트를 차례로 돌린다. 여기서 깨지면 그 패키지를 미완료로 되돌린다.

### 쟁점 D. 알림 제한과 판정을 누가 소유하는가 (8번, 30번, 31번)

- WP5는 알림 리듀서를, WP1은 세션 만료 알림을, WP6은 90일 판정을 필요로 한다.

**결정.** 여러 패키지가 같은 규칙을 쓰는 순수 함수는 공유 core에 두고 기반 작업이 구현·테스트한다: core/notify.ts, tripStatus.ts의 isTrackExpired·retentionUntil·isRetentionExpired, core/group.ts, core/chatOrder.ts, core/sha256.ts, core/kv.ts(memoryKV). 기반 작업의 양은 늘지만 패키지끼리 기다리는 경로가 없어진다.

## 9. 검증 게이트

### 9.1 작업 중 게이트 (패키지가 스스로)

`node scripts/gate-scope.mjs WPn` 하나로 돈다. 스크립트는 허용된 명령만 부른다.

1. `npx tsc --noEmit` 결과에서 WPn 소유 파일의 오류가 0건
2. `node --disable-warning=MODULE_TYPELESS_PACKAGE_JSON --import ./tests/setup/resolve-ts.mjs --test "tests/wpn-*.test.ts"` 통과
3. `YT_SCOPE=WPn`으로 foundation 테스트를 돌려 WPn 소유 파일의 위반이 0건

완료 보고 직전에 `npx expo export --platform web --output-dir /tmp/yt-export-wpn`을 한 번 돌린다. 실패 원인이 남의 파일이면 고치지 않고 보고만 한다.

### 9.2 통합 게이트 (통합 담당만, 순차)

1. `npx tsc --noEmit`
2. `npm test`
3. `npx expo export --platform web --output-dir /tmp/yt-export`
4. `grep -rn -e '여정' -e 'yeojeong' src App.tsx app.config.js README.md` 0건
5. src에서 legacy-v1과 삭제 경로(core/extract.ts, core/planner.ts, services/google·local·maps, store/useTrip, ui.tsx) import 0건
6. /tmp/yt-export 자산의 ttf가 정확히 4개
7. golden-e2e의 todo를 풀고 통과

개발 서버는 띄우지 않는다. git 커밋·푸시·브랜치 조작을 하지 않는다.
